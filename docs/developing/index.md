# 开源发展现状与社区协作指南

当公司使用开源软件项目时，他们需要了解许可和合规情况，检查项目的健康状况，确保没有安全漏洞，并且在某些情况下，还要识别有才华的社区成员，以便进行潜在的招聘流程。

开源蓬勃发展，社区文化应尽可能开放与透明。信息自由且公开地获取，这在许多非开源项目是无法达到的。信息往往经过繁文缛节处理，普通用户／开发者根本无法获得，更别说那些试图为项目开源做出贡献的人了。

分布式协作模式(Distributed modes of collaboration)，即大型团队在没有集权的情况下协同工作，效果极佳。
新兴社区和组织常常被质疑、严密监控，甚至在某些情况下被起诉，最终因害怕新思想出现或其他原因而关闭。

一个人or一个组织抵制变革的最大且最常见的原因是对未知的恐惧。比如对新技术的恐惧，对新工具，新工作流，新协助方式，新语言的`不会`的挑战，因为`不会`带来的无权威感的恐惧

信任在欠发达地区是稀缺产物。

## 发展中国家开发者面临的开源挑战

经济挑战是发展中国家开发者开源面临的最明显挑战，影响着这些地区的开源开发者和社区。

开源工作者获取最新最强机器是一大挑战；稳定高速的互联网连接也是必需的，[Watt Toolkit](https://steampp.net/) 提供了一定的帮助。

开源工作者应该是一个这样的画像：

面对任何使得自己贡献项目的挑战，去战胜挑战。

任何技术、信息联通的问题使得自学和学习受到阻碍的障碍都应该被打破。
开源开发者自主选择一个开源项目，自己学习并开始贡献 PR 内容。

## 社区支持方案

为了打破，项目最终由拥有稳定高速互联网连接和最新设备的少数特权者维护，我们提供了基础的 github 团队协助 帮助服务

我个人多次见过。有人会开始学习开源项目，研究某个特定的技术栈或提升技能，并开始为其贡献。但一旦有偿工作机会出现，即使是第二份工作，他们也完全放弃了开源项目。这很合理。每个人都必须优先考虑为自己和家人谋生的手段。

我们 开源组织社区 努力建设 营销活动、社区建设活动以及文档本地化(就是多语言文档，将英语翻译成其他语言，比如各 开发工具的 中文网，中文教程，中文文档)

英语是互联网的语言，能够理解代码和理解文档、架构资源和技术规范，从而能够为开源项目做出有意义的贡献。找到进入开源项目的切入点。为此使用英语中去学习英语是一条很切合实际的路线。

我们的同事旨在实现开发者可能拥有的每一行代码、贡献或想法的变现。任何参与外部开源项目都是值得欢呼的。
对应公司内部的项目，我们签署必要的协议，并鼓励同事将参与的项目分享到 开源组织的文档中，让公司感兴趣的同事参与进去，这也实现了必要的监督与开源共建。我们不认为这是危险的，因为开源带来 规模效应与 全球开发者的共同协作。这是有益于地区发展与公司发展的，当然和开源组织发展密切相关。

一切都始于个人。随着我们每个人都“众包”开放文化，我们生活和工作的地区的文化也在变化。尽你所能，把开源带到你的社区，看看会带你去哪里。

## 平等友好沟通准则

我们通常使用低语境、直接、提供必要的上下文的方式去、进行直白的沟通。

我们邮件/社区的沟通的语言是英语。我们从未把这当作规则，但几乎所有人都用英语交流。一个英语不流利的人可能会说得很尴尬，而另一个人可能会因此产生负面反应。但我觉得这种情况其实很少见。对彼此友好。而且大家彼此之间监管得相当好;如果有问题，通常都是短暂的。

如果我给某个特定的人发邮件，我会用他们发给我的邮件作为参考，猜测他们更喜欢高语境还是低语境的回答。如果不知道，我可能会默认使用较低的上下文模式。这意味着我会很快切入主题，但可以先铺垫一些背景。

如果我写作面向更广泛的受众（比如给邮件列表发送邮件、在网站发布公告等），我也会采用较低上下文的沟通模式。这在网站上更为重要，因为如果网站内容太冗长，很多读者可能会选择退出

除此之外，我建议你始终假设是积极的。如果有人通过邮件联系你，要摒弃对其沟通方式的任何先入为主的观念，找到他们想传达的信息。高语境沟通者很少能直接直面问题，所以你可能需要更仔细地阅读。低语境的沟通者可能显得很直白，但他们只是想快速切入重点。
